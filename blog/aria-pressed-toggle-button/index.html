Build a Toggle Button with aria-pressed

Expose an on/off button state with aria-pressed and a stable label. Keep application behavior, visual feedback and keyboard activation synchronized.

By Penta AIPublished 15 November 20262 min read

In this guide

  1. Start with one button and one state
  2. Make the state visible without renaming the control
  3. Check every route that changes the state

Use aria-pressed on a button that toggles a persistent on/off state, such as pinning a preview. Keep the label stable and update the pressed value when the actual state changes. The attribute communicates state; it does not implement the application behavior.

Start with one button and one state

<button id="pin-preview" type="button" aria-pressed="false">
  Pin preview
</button>
const pin = document.querySelector("#pin-preview");
pin.addEventListener("click", () => {
  const next = pin.getAttribute("aria-pressed") !== "true";
  // Apply the real preview-pinning behavior here.
  pin.setAttribute("aria-pressed", String(next));
});

This example demonstrates state wiring, not a complete pinning feature. In a real component, derive the attribute from the same state that controls whether the preview is pinned. If an asynchronous operation can fail, decide when state becomes confirmed and how the interface restores or explains a failed change.

Reference: MDN aria-pressed reference.

Make the state visible without renaming the control

#pin-preview[aria-pressed="true"] {
  background: #e7f0ff;
  border: 2px solid #174fa0;
  font-weight: 700;
}

The stable Pin preview label identifies the same toggle in both states. A separate design that changes an action label from Pin preview to Unpin preview can use an ordinary action-button pattern instead. Avoid combining contradictory labeling and state conventions.

Do not use aria-pressed for the current navigation page, a selected tab or a form checkbox just because the item looks highlighted. Those patterns have different semantics. A checkbox may be the better native control when the value belongs to a submitted form.

Check every route that changes the state

  • Activate with mouse, Enter and Space and confirm one state change.
  • Restore a saved setting and verify visual and semantic states agree.
  • Change the state elsewhere in the application and inspect the button again.
  • Check visible focus independently of the pressed appearance.
  • Listen for the name, role and state in a screen reader.

The mixed value is for a toggle controlling items with different states, not an automatic loading indicator. Keep loading feedback separate. Record the state source and failure behavior beside the button state specification so the semantic attribute stays synchronized as the feature grows.
