Keep Accordion Buttons and Panels in Sync with aria-expanded

Implement a custom disclosure with a native button, explicit expanded state and matching panel visibility. Test keyboard operation and focus when content closes.

By Penta AIPublished 16 November 20262 min read

In this guide

  1. Connect one heading button to one panel
  2. Separate expansion from other control states
  3. Review interaction and reading order

For a custom accordion, put a native button inside an appropriate heading, expose its expanded state and keep that state synchronized with the associated panel. Use native details and summary instead when they already meet the requirement; custom markup means owning the additional behavior.

Connect one heading button to one panel

<h3>
  <button id="format-toggle" type="button"
    aria-expanded="false" aria-controls="format-panel">
    Export format notes
  </button>
</h3>
<div id="format-panel" hidden>
  <p>Choose the format required by the receiving tool.</p>
</div>
const toggle = document.querySelector("#format-toggle");
const panel = document.querySelector("#format-panel");
toggle.addEventListener("click", () => {
  const expanded = toggle.getAttribute("aria-expanded") === "true";
  toggle.setAttribute("aria-expanded", String(!expanded));
  panel.hidden = expanded;
});

This example allows the panel to open and close independently. The h3 level is only appropriate when it fits the containing page. Give each instance unique IDs, and ensure component CSS does not override hidden in a way that leaves a supposedly closed panel visible.

Reference: W3C ARIA Authoring Practices accordion pattern.

Separate expansion from other control states

Aria-expanded describes whether controlled content is expanded. Aria-pressed describes a toggle button’s pressed state and is not a substitute here. Keep the visible label meaningful in both states, and give the button a clear focus indicator.

For a multi-panel accordion, decide whether several sections can remain open. If another action closes a panel that contains keyboard focus, restore focus to a useful visible control. Do not collapse content silently while leaving focus in an unavailable descendant.

Review interaction and reading order

  • Tab to each heading button and activate it with Enter and Space.
  • Verify the exposed expanded value after every change.
  • Reach links and controls inside an open panel.
  • Close the panel and confirm its descendants leave the normal interaction path.
  • Test long headings, enlarged text and repeated component instances.

Arrow-key navigation between headers is an optional pattern choice; ordinary native buttons still need a working Tab sequence. Avoid making every small panel a named landmark when that would create excessive regions. Compare this implementation with the native disclosure guide and document why the custom behavior is needed.
