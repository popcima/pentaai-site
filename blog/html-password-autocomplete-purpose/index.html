Label Password Fields with the Correct Autocomplete Purpose

Use current-password and new-password for their intended tasks. Keep labels, paste and password-manager behavior usable across sign-in and password changes.

By Penta AIPublished 18 November 20261 min read

In this guide

  1. Describe a password-change form accurately
  2. Review assistance instead of fighting it
  3. Test the complete task with specimen credentials

Password fields need both a human-readable label and an accurate autocomplete purpose. Use current-password when requesting the existing credential, and new-password when creating or replacing one. The distinction helps browsers and password managers understand the task without guessing from visual position.

Describe a password-change form accurately

<label for="existing-password">Current password</label>
<input id="existing-password" name="currentPassword"
       type="password" autocomplete="current-password">
<label for="replacement-password">New password</label>
<input id="replacement-password" name="newPassword"
       type="password" autocomplete="new-password">
<label for="repeat-password">Confirm new password</label>
<input id="repeat-password" name="confirmPassword"
       type="password" autocomplete="new-password">

Add the application’s required and validation rules deliberately. A confirmation field also requests the new password; there is no separate confirm-password autocomplete token. In a sign-in form, identify the account field with autocomplete="username", even when that account identifier is an email address.

Reference: MDN autocomplete field purposes.

Review assistance instead of fighting it

Autocomplete tokens provide guidance; the browser or password manager decides how to offer suggestions and filling. Do not claim the attributes guarantee an identical popup in every environment. Test saved credentials and generated-password behavior in the combinations the product supports.

Keep paste available. Avoid clearing a field merely because its value appeared without the exact keystrokes your handler expected. A reveal-password control should be a clearly named button with type="button" so checking the value does not submit the form unexpectedly.

Test the complete task with specimen credentials

  • Fill the existing credential from a password manager.
  • Generate a new password and confirm it.
  • Paste a long value and inspect wrapping of instructions and errors.
  • Check focus, reveal controls and validation without logging passwords.

Use a test account or isolated fixture, and never print credential values into a diagnostic report. The frontend should describe actual server requirements rather than inventing a strength guarantee from a decorative meter. For the basic field relationship, keep persistent labels visible even after autofill; autocomplete is metadata, not a replacement for instructions.
