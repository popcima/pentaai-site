CSS Logical Properties: Layouts That Follow Text Direction

Replace direction-dependent spacing with logical CSS properties. Understand inline and block axes, test RTL content, and preserve intentional physical placement.

By Penta AIPublished 26 October 20263 min read

In this guide

  1. Understand inline and block axes
  2. Build a direction-aware notice
  3. Use layout gaps for sibling spacing
  4. Watch for conflicting declarations
  5. Define what should not mirror

Logical CSS properties describe layout relative to the writing mode and direction. They help a component keep a “start” edge or consistent inline padding when text direction changes. Use them where the design follows reading flow, while retaining physical coordinates for effects that intentionally belong to a fixed side.

Start with a simple notice or navigation item rather than mechanically replacing every occurrence of left and right in a large stylesheet. A focused component makes it easier to see which relationships should adapt and which should remain unchanged.

Understand inline and block axes

In ordinary horizontal English text, the inline axis runs across the line and the block axis runs through successive lines. Changing direction changes the start and end of the inline flow; vertical writing modes also change how the axes map to physical dimensions. MDN’s logical properties guide explains these mappings.

Physical habitFlow-relative alternative
padding-left and padding-rightpadding-inline
margin-top and margin-bottommargin-block in horizontal writing
A border on the reading-start edgeborder-inline-start
Left-aligned reading contenttext-align: start
Width along the text lineinline-size

The alternatives express intent rather than serving as universal text substitutions. For example, physical width and inline size are equivalent in a horizontal writing mode but represent different physical dimensions when the writing mode changes.

Build a direction-aware notice

.notice {
  border-inline-start: .25rem solid #0f7fff;
  padding-block: 1rem;
  padding-inline: 1.25rem;
  margin-block: 1.5rem;
  text-align: start;
}
.notice-title { margin-block: 0 .5rem; }

Place this component in both a left-to-right context and a context marked with dir="rtl". The accent border should follow the reading-start edge without a second rule that manually moves it to the other side. Use meaningful content in each context when reviewing the actual experience.

Use layout gaps for sibling spacing

For an icon and label, a flex or grid gap usually describes their separation more clearly than a margin added to one physical side of the icon. Confirm source order and alignment first. Adding row-reverse just to fix a spacing problem can alter the visual order without addressing the underlying structure.

Keep the document’s semantic order sensible for the intended reading sequence. Logical properties do not translate text, resolve every bidirectional-content issue or automatically mirror directional graphics. Review arrows, progress indicators and mixed text such as identifiers as separate content decisions.

Watch for conflicting declarations

During a migration, an older physical margin and a newer logical margin can affect the same edge. Inspect the computed result and the winning declaration rather than assuming the logical version always takes precedence. Remove obsolete rules once you have verified the intended replacement.

Change a small family of related properties at a time. For example, migrate the notice’s accent edge and padding together, then test it before changing all navigation spacing. This keeps a directionality repair from becoming a difficult-to-review site-wide restyling.

Define what should not mirror

A decorative light source or a background illustration may intentionally remain in the same physical position. Record that choice. The goal is to follow the content’s direction where appropriate, not to reverse every visible feature of the page.

Finish with a component matrix covering both directions, long labels, nested content and narrow widths. Add the result to the handoff checklist. A successful migration has an understandable flow-relative rule and clear exceptions, rather than two increasingly different stylesheets for the same component.
