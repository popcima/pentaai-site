Inspect Roles and Names in Chrome’s Accessibility Tree

Use Chrome DevTools to trace a control’s computed role, name and state. Compare the DOM with exposed semantics, then verify the real keyboard interaction.

By Penta AIPublished 15 November 20262 min read

In this guide

  1. Select the real control and inspect computed properties
  2. Compare the DOM with the accessibility tree
  3. Verify behavior after the semantic repair

Use Chrome DevTools’ Accessibility tools to inspect what the browser exposes about an element’s role, name and state. This helps explain why a visible label is missing or why a control has unexpected semantics. It complements keyboard and screen-reader testing; it does not replace them.

Select the real control and inspect computed properties

  • Open DevTools and select the element in the Elements panel.
  • Open the Accessibility tab, using the additional-tabs menu if it is hidden.
  • Review the computed role, accessible name and relevant state.
  • Expand name sources when available to see which text or attribute contributed.

For a fictional Save notes control, expect a button role and a concise name that matches its visible purpose. If the name is an unrelated icon label, inspect the icon and any aria-label or aria-labelledby on the control. Repair the source of the name instead of adding another competing naming attribute.

Reference: Chrome DevTools accessibility features reference.

Compare the DOM with the accessibility tree

Use the accessibility-tree view to see the element’s position among exposed nodes. A decorative wrapper may not appear as a separate meaningful node, while a button does. The accessibility tree is not a one-to-one copy of every DOM element.

When a node is missing, inspect hidden states and ancestors. A visually present descendant of aria-hidden content may be excluded from accessibility exposure. Conversely, text that is merely positioned offscreen can still be exposed. Confirm which behavior the component actually needs before changing its CSS.

Check the interface in the state where the bug occurs. A collapsed menu, open dialog and loaded results panel can expose different nodes and properties. Capture the selected element and the state trigger so another developer can reproduce the same tree.

Verify behavior after the semantic repair

  • Reach the control using Tab and Shift+Tab.
  • Activate it with its expected keyboard inputs.
  • Inspect its state after activation and after a failure.
  • Review the relevant heading or landmark context.
  • Listen with a supported screen reader rather than relying on the tree alone.

A correct name in DevTools does not prove that focus is visible, a menu can be closed or a touch target is usable. Record the observed role, name and state alongside the interaction result. For naming repairs, use the name-versus-description guide to keep identity and supporting help separate.
