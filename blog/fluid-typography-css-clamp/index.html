Fluid Typography with CSS clamp(): A Worked Example

Create headings that scale between readable limits with CSS clamp. Calculate a fluid range, combine rem and viewport units, and test zoom behavior.

By Penta AIPublished 26 October 20263 min read

In this guide

  1. Calculate the preferred value
  2. Choose limits using content
  3. Keep body text decisions separate
  4. Test zoom and user text settings
  5. Document the intended behavior

CSS clamp() lets a font size grow between a minimum and maximum. Choose readable endpoint sizes first, calculate the expression between them, and test the result with real text and browser zoom. A mathematically smooth curve is not enough if the heading breaks its layout or stops responding well to user preferences.

This example builds a heading that measures 32px at a 400px viewport and 56px at a 1200px viewport under a 16px root-font assumption. Those dimensions are a worked design choice, not a recommended scale for every website.

Calculate the preferred value

The size difference is 24px across 800px of viewport width. The slope is 0.03, which becomes 3vw. To reach 32px at a 400px viewport, add a 20px intercept. Expressing the intercept and bounds in rem preserves a relationship with the root font size.

.hero-title {
  font-size: clamp(2rem, 1.25rem + 3vw, 3.5rem);
  line-height: 1.1;
  max-width: 18ch;
}

If the root size changes, the rem terms change too, so these numeric endpoints shift. Treat the table as an explanation of one condition, not as a promise of exact sizes in every browser configuration. MDN’s clamp reference explains the minimum, preferred and maximum arguments.

Choose limits using content

Test the longest plausible heading, not only a short marketing phrase. Look for awkward single-word lines, overlap with nearby controls and excessive height on a small phone. A comfortable font size can still need a narrower line measure or a different layout.

The ch unit in the example provides a rough character-related measure based on the font’s zero glyph; it is not an exact character count. Compare the actual typeface. Two fonts at the same CSS size and width can produce noticeably different line breaks.

Keep body text decisions separate

A large display heading can benefit from substantial variation, while body text may need a much narrower range or no fluid scaling. Start body copy at a readable size with an appropriate line height. Avoid shrinking paragraphs solely to preserve a desktop composition on mobile.

Use a small set of role tokens if several headings share the pattern. For example, keep one display size and one section-title size instead of assigning an unrelated clamp expression to every component. That gives the next designer a few understandable controls rather than a page full of independent curves.

Test zoom and user text settings

Combining rem and viewport units does not automatically guarantee accessible resizing. Browser zoom changes the effective CSS viewport as well as text rendering, which can counteract some viewport-based growth. Test 200% zoom, increased default font size, and narrow reflow with the actual page.

WCAG’s resize-text guidance focuses on allowing text to enlarge without losing content or functionality. Check that buttons, cards and navigation can grow with the text. If a particular clamp range prevents sufficient resizing, revise the expression or use a simpler relative size.

Document the intended behavior

Record the two endpoint assumptions, the font family, line height and line measure alongside the token. Include a screenshot at the narrow, middle and wide widths and a note about the zoom checks you performed. That is more useful than handing over an unexplained formula.

If text still looks wrong, confirm the rendered font with the font inspection workflow. If it extends beyond its container, use the overflow guide to diagnose the layout instead of repeatedly reducing the font size.
