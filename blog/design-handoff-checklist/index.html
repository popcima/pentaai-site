A Design Handoff Checklist Developers Can Verify

Hand off a website with clear tokens, assets, responsive rules and interaction states. Use acceptance criteria that can be checked in the running interface.

By Penta AIPublished 26 October 20263 min read

In this guide

  1. 1. Record the reference conditions
  2. 2. Deliver tokens with their roles
  3. 3. List assets and their behavior
  4. 4. Describe responsive and interactive behavior
  5. 5. Write acceptance criteria as observable outcomes
  6. 6. Review the running implementation

A useful design handoff tells the developer what should happen, which details are fixed, and how to verify the result. Screenshots help establish visual intent, but they do not explain responsive behavior, focus states, asset variants or what to do when content changes. Pair the reference with a small set of observable acceptance criteria.

Start by naming the pages and components included in the handoff. Separate approved decisions from open questions. If a team has only reviewed the homepage, avoid presenting the resulting notes as a complete product-wide design system.

1. Record the reference conditions

FieldExample to adapt
Page and statePricing page, annual option selected
ViewportNarrow, middle and wide reference widths
ThemeLight and dark where supported
ContentRealistic titles, prices and error messages
Source of truthDesign file version and implementation branch

Use real or clearly labeled example content. A layout reviewed with three short words can fail when a real product name wraps. Include at least one long-content case for navigation, cards and buttons so implementation decisions are made before the final review.

2. Deliver tokens with their roles

Provide the active typography, color, spacing, radius and elevation values. Explain what each semantic token controls and identify exceptions. A developer should know whether a value is an intentional rule or a measurement from one reference screenshot.

For an existing website, use the design-system inventory workflow to separate observation from inference. If the implementation uses CSS variables or Tailwind, include the intended mapping rather than leaving a second round of naming decisions to the recipient.

3. List assets and their behavior

Include the editable asset source where appropriate, export variants, intended dimensions and relevant usage permissions. State whether each icon is decorative or conveys meaning. Identify logos or illustrations that need a different treatment on dark backgrounds.

For fonts, record the actual family, required weights, fallback stack and delivery location. Avoid asking the developer to infer a font from a screenshot when a source file or known family name is available. Link to the icon-format guide when export choices need explanation.

4. Describe responsive and interactive behavior

Specify which layouts wrap, stack, scroll locally or change navigation mode. For important controls, include default, hover, keyboard focus, disabled, loading and error states as applicable. State where focus should go after a dialog opens or an action changes the page.

Chrome’s device-mode documentation provides a useful way to inspect viewport changes, while noting the limits of simulation. Add a real-device check for interactions or performance concerns that emulation cannot settle.

5. Write acceptance criteria as observable outcomes

Component: guide card
- A long title wraps without overlapping the category label.
- The entire page fits a 320 CSS pixel viewport.
- The cover keeps its intended aspect ratio.
- The link has a visible keyboard focus indicator.
- Light and dark text/surface pairs are checked separately.
- The card remains usable when text is enlarged.

Open question:
- Should every card be equal height when summaries vary?

Avoid criteria such as “looks premium” without a reference or an observable meaning. A specific statement like “title and button do not overlap at narrow widths” can be checked and resolved. Keep subjective design feedback, factual defects and open product decisions distinguishable.

6. Review the running implementation

Compare representative pages at the agreed widths, then interact with them. Review keyboard focus, longer content, missing images and error states. WCAG’s reflow guidance is a useful reference for checking content access as the layout narrows, rather than judging only a fixed desktop image.

Record each issue with the page, state, expected result and observed result. Assign an owner to unresolved questions. When a decision changes, update the specification as well as the implementation so the two do not drift apart.

For an AI-assisted build, put the reviewed decisions into a DESIGN.md brief and explicitly direct the coding tool to read it. The checklist remains the human-readable acceptance record: it tells everyone what evidence is needed before the handoff is complete.
