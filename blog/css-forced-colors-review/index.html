Review Your Interface in Forced Colors Mode

Check borders, focus indicators and selected states in forced colors mode. Use system colors for targeted repairs while preserving the user’s palette.

By Penta AIPublished 27 October 20262 min read

In this guide

  1. Give controls a structural boundary
  2. Inspect information that may disappear
  3. Use a repeatable inspection path

Forced colors mode replaces parts of the page palette with colors chosen by the user and browser. A control that depends on a subtle shadow or gradient can lose its visible boundary. Review the interface in this mode and repair the missing information, while allowing the user’s palette to remain in control.

Give controls a structural boundary

.sample-action {
  border: 2px solid transparent;
  box-shadow: 0 2px 8px rgb(0 0 0 / 15%);
}
.sample-action:focus-visible {
  outline: 3px solid #174fa0;
  outline-offset: 3px;
}
@media (forced-colors: active) {
  .sample-action { border-color: ButtonText; }
  .sample-action:focus-visible { outline-color: Highlight; }
}

The transparent border reserves space in the ordinary design, so exposing it in forced colors does not need to change the component’s dimensions. These system color keywords follow the active palette. Check the result with native buttons instead of assuming that a visually button-like div will receive equivalent browser treatment.

Reference: MDN: forced-colors media feature.

Inspect information that may disappear

Shadows are suppressed in forced colors, and non-URL background images such as gradients can be removed. Review boundaries, state indicators and diagrams that rely on those effects. A selected tab with only a background tint may need a visible border or another persistent indicator. Do not use a color swatch as the only label for a choice.

Avoid setting forced-color-adjust: none on an entire application to preserve brand colors. That opts content out of the user’s chosen adaptation. A narrowly scoped exception may be needed for meaningful artwork, but its purpose and readability should be reviewed independently.

Use a repeatable inspection path

  • Visit navigation, forms, dialogs and the main task flow.
  • Move keyboard focus through every interactive component.
  • Check selected, checked, disabled and error states.
  • Inspect icons and text over images as well as plain surfaces.

Use browser emulation to find likely issues, then test the relevant operating-system mode on a supported device before making broad accessibility claims. Capture the exact environment and palette used. A light palette and a dark palette can expose different assumptions in the same component.

For a useful bug report, describe the lost information: “the unselected option has no visible boundary” is more actionable than “the colors look wrong.” Attach ordinary and forced-color views of the same state, and keep repairs close to the component that needs them.
