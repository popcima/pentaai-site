Choose Plain-Text Editing Deliberately with contenteditable

Use plaintext-only for a custom editable surface, keep its accessible name and focus visible, and account for submission and paste behavior beyond the attribute.

By Penta AIPublished 22 November 20261 min read

In this guide

  1. Name the editable surface explicitly
  2. Account for what native controls normally provide
  3. Test real editing paths and unsupported behavior

Contenteditable="plaintext-only" enables editing without retaining rich text formatting from the editing interaction in supporting browsers. It can suit a custom text surface, but it does not turn a div into a native form field. For an ordinary multiline form value, textarea is often the simpler starting point.

Name the editable surface explicitly

<p id="notes-label">Review notes</p>
<div contenteditable="plaintext-only" role="textbox"
     aria-multiline="true" aria-labelledby="notes-label"
     class="notes-editor"></div>
<style>
.notes-editor { min-block-size: 5rem; padding: .75rem; border: 1px solid; }
.notes-editor:focus-visible { outline: 2px solid #174f99; outline-offset: 3px; }
</style>

The role and label explain the custom surface to accessibility APIs; the visible outline identifies focus. The example deliberately does not claim to implement saving, form validation or a complete editor. Those behaviors need explicit application design.

Reference: MDN contenteditable.

Account for what native controls normally provide

A contenteditable div is not automatically serialized as a named form value. Decide how to read, normalize and save its text, including line breaks. Do not treat a name attribute added to the div as equivalent to a textarea’s name.

Contenteditable is enumerated, with meaningful values including false and plaintext-only. Missing or invalid values can inherit editability from an ancestor. The plain-text editing mode is also not a general sanitizer for HTML that other application code inserts.

Test real editing paths and unsupported behavior

Type several lines, paste formatted text, undo, select a range and use an input method. Inspect both the visible result and stored text. Test the browsers and assistive technology your interface supports, and keep a usable fallback where the desired editing mode is unavailable.

Compare the effort with a labeled textarea before committing to a custom editor. Use persistent labeling and the caret and selection guide to review the editing experience itself.
