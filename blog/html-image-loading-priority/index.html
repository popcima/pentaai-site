Choose Image Loading Priority Without Slowing the Hero

Distinguish lazy loading from fetch priority. Identify the likely LCP image, keep it discoverable and verify image requests under realistic loading conditions.

By Penta AIPublished 28 October 20262 min read

In this guide

  1. Give the two images different jobs
  2. Separate discovery, scheduling and display
  3. Verify a repeatable loading scenario

Do not lazy-load an image that needs to appear immediately in the initial viewport. For an important hero image, make the resource discoverable in the HTML and consider a high fetch-priority hint after confirming its role. Reserve lazy loading for images that can wait until the reader approaches them.

Give the two images different jobs

<!-- Example hero: visible when the page opens -->
<img src="/images/interface-hero.webp" width="1200" height="675"
     fetchpriority="high"
     alt="A layout preview beside its spacing notes">

<!-- Example figure farther down the page -->
<img src="/images/detail-example.webp" width="900" height="600"
     loading="lazy"
     alt="The selected card with its padding highlighted">

Supply real assets with these dimensions or change the dimensions to match your files. The examples illustrate different loading roles, not a rule that every page must contain one high-priority image. A text block can be the Largest Contentful Paint element instead.

Reference: web.dev: optimize Largest Contentful Paint.

Separate discovery, scheduling and display

loading="lazy" affects when a resource is eligible to load. fetchpriority supplies a priority hint; it does not guarantee an immediate request or fast rendering. Image size, server response, discovery timing and other work can still delay the visible result. Adding high priority to many resources also makes the intended preference less useful.

If a hero is inserted only after JavaScript runs, first investigate that late discovery. A priority hint attached at the same late moment cannot recover the time before the browser knew the image existed. Likewise, compressing a large asset and serving an appropriate source remain separate responsibilities.

Verify a repeatable loading scenario

  • Identify the LCP element in a performance recording.
  • Inspect when its request starts and how it competes with other resources.
  • Compare a fresh load with consistent throttling and viewport settings.
  • Check that lower-page images still load as the reader approaches them.

Keep dimensions in the markup to reserve space and check responsive source selection separately. Record the environment and before/after measurements when claiming an improvement. A successful image request or a high-priority label in DevTools does not by itself establish a faster experience for visitors.
