Find Which Element Wins a Pointer Hit Test

Probe viewport coordinates with elementFromPoint, inspect overlay interception, and separate pointer hit testing from keyboard focus and accessibility.

By Penta AIPublished 23 November 20262 min read

In this guide

  1. Probe a point inside the visible button
  2. Trace the returned element before changing z-index
  3. Check the rest of the interaction path

When a visible button will not respond, elementFromPoint can identify the topmost hit-testable element at a chosen viewport coordinate. It helps investigate an intercepting overlay, but it does not explain every reason a click handler fails.

Probe a point inside the visible button

const button = document.querySelector('#save-review');
if (button) {
  const rect = button.getBoundingClientRect();
  const x = rect.left + rect.width / 2;
  const y = rect.top + rect.height / 2;
  const hit = document.elementFromPoint(x, y);
  console.log({ hit, insideButton: hit !== null && button.contains(hit) });
}

Run this after bringing the button into the viewport. A nested icon or label can be the returned element, so the containment check is more useful than requiring hit === button. A clipped or partly covered button may need probes at several visible points rather than only its bounding-box center.

Reference: MDN elementFromPoint pointer hit testing.

Trace the returned element before changing z-index

If an unrelated overlay wins the test, inspect its bounds, stacking context and pointer-events value. Elements with pointer-events:none are skipped by this API. Removing hit testing from a decorative layer may be appropriate, while an intentional modal backdrop needs different behavior.

The coordinates are viewport-relative. Passing document coordinates without accounting for scrolling can inspect the wrong location. A point outside the viewport can return null, and a hit inside another document can return its iframe element rather than an internal descendant.

Check the rest of the interaction path

After fixing an unintended interception, activate the control by pointer and keyboard. Check disabled state, event listeners and navigation behavior separately if it still does nothing. The hit-test result alone does not establish focusability or an accessible name.

Record the viewport, scroll position and chosen point with the returned node. This makes a bug report more actionable than a statement that “the button is under something,” especially when the obstruction changes at a breakpoint.
