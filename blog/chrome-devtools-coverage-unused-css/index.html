Use Chrome Coverage Without Deleting Needed CSS

Investigate unused CSS with DevTools Coverage. Record interactive states, distinguish unobserved rules from dead code and verify removals across routes.

By Penta AIPublished 27 October 20262 min read

In this guide

  1. Record a task, not only a screenshot
  2. Classify an unused rule before removing it
  3. Make a small, reversible cleanup

Chrome’s Coverage panel shows which parts of a loaded resource were used during the recorded session. Unused in that session does not mean safe to delete from the application. A menu, error state or responsive layout may need rules that your first page load never exercised.

Record a task, not only a screenshot

  • Open DevTools, then use the Command Menu to show Coverage.
  • Start the reload-and-record action.
  • Perform the page’s main interactions while recording continues.
  • Open a CSS resource to inspect the used and unused regions.

Reference: Chrome DevTools: Coverage.

For a sample export page, open its options, trigger a validation error with harmless sample input, dismiss the error and complete the preview flow. Repeat at the relevant responsive widths. Write down the path you exercised so the report has a defined scope.

Classify an unused rule before removing it

/* Example investigation notes, not a deletion list */
.export-error   -> only visible after failed validation
.mobile-tools   -> only displayed at narrow widths
.legacy-banner  -> no current template reference found

The first two candidates need additional state coverage. The third may deserve a source search, but a missing template match is still only evidence: classes can be generated dynamically or supplied by content. Trace the component owner and route usage before deciding the rule is obsolete.

A shared stylesheet can serve several pages. Recording one route does not establish that its unused rules are unnecessary elsewhere. Likewise, print styles, theme rules and interaction selectors may have conditions outside your initial session. Keep those conditions in the review notes rather than treating a single percentage as a site-wide verdict.

Make a small, reversible cleanup

Remove only a well-understood set of obsolete rules in source. Rebuild and exercise the routes and states that previously depended on the file. Compare the resulting resource size and behavior. Do not claim a loading-speed improvement from a smaller unused percentage alone; performance requires its own measurement.

  • Check the component’s normal, loading, empty and error states.
  • Review the widest and narrowest supported layouts.
  • Inspect keyboard focus and open overlays.
  • Confirm that production builds preserve dynamically used classes.

For handoff, include the recording scope, candidate rules, source ownership and validation performed. That turns Coverage into an investigation tool instead of an automatic deletion instruction. The useful outcome is a stylesheet with a clearer purpose and no lost interface states, not merely a greener report.
