Why an HTML Download Link Opens in the Browser

Inspect same-origin rules, response headers and suggested filenames when a download link behaves unexpectedly. Keep labels honest about file type and destination.

By Penta AIPublished 15 November 20262 min read

In this guide

  1. Start with a real same-origin file
  2. Inspect the final response
  3. Test the file, not just the click

The download attribute asks the browser to treat a linked resource as a download, but it is not an unconditional command for every URL. Check the resource’s origin, redirects and response headers before changing the button styling or adding a click handler.

Start with a real same-origin file

<a href="/downloads/design-review.txt" download="design-review.txt">
  Download the design review checklist (TXT)
</a>

Place the actual file at the illustrated path. The download value suggests a filename; it does not create the file or convert its contents. A descriptive label tells the reader what is being requested before the browser opens a save prompt or handles it another way.

Reference: MDN anchor download attribute reference.

Inspect the final response

The attribute applies to same-origin resources and supported blob or data URLs. For an unrelated remote URL it may be ignored, although that server can independently request attachment handling through its response. A redirect to another origin is therefore worth checking when a formerly working link changes behavior.

In the Network panel, inspect the request status, final URL, Content-Type and Content-Disposition. A server-provided filename can take precedence over the filename suggested in HTML. A successful HTTP response can still contain an error document or login page, so inspect what the response actually represents.

Browser settings and platform behavior affect whether users see a prompt, an automatic save or an opened file. Do not promise an exact dialog sequence in the interface. If you do not control a remote provider’s headers, link to its documented download destination instead of trying to bypass browser restrictions.

Test the file, not just the click

  • Request the file from a fresh session and check whether authentication is required.
  • Verify the saved filename, extension and contents.
  • Test a missing-file response and an expired download URL.
  • Check that the label matches the delivered format.
  • Try the supported desktop and mobile browsers.

If the application must generate a report first, show a button for that action and provide the real file link when it is ready. Do not announce completion merely because a user activated the control. Use the button-versus-link distinction to separate generation from navigation, and keep a recovery path when file creation fails.
