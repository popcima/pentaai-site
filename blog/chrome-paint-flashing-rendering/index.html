Use Paint Flashing to Investigate Unexpected Repaints

Find repaint regions with Chrome’s Rendering panel, then measure the interaction in Performance. Separate a diagnostic highlight from proof of a bottleneck.

By Penta AIPublished 15 November 20262 min read

In this guide

  1. Choose one repeatable interaction
  2. Trace the highlighted region to a cause
  3. Keep only a justified repair

Paint flashing highlights regions Chrome repaints during an interaction. Use it to spot unexpectedly broad repainting, then investigate the cost with a performance recording. A green flash is a diagnostic clue, not a score or proof that the interface is slow.

Choose one repeatable interaction

Start with a short task such as hovering one card, scrolling a results panel or opening a preview. Keep the content, viewport and browser state consistent. An entire page loading for the first time naturally paints many regions and is a poor comparison for a small hover effect.

  • Open DevTools’ command menu and find the Rendering panel.
  • Enable Paint flashing.
  • Perform the chosen interaction several times.
  • Note which areas repaint and whether they extend beyond the changed component.

Reference: Chrome DevTools rendering performance reference.

Trace the highlighted region to a cause

Inspect the styles and DOM changes associated with the interaction. A small hover can change an ancestor’s background, trigger an expensive effect or update unrelated content through application code. Turn off one suspected declaration or update at a time in a local reproduction.

Separate repainting from layout shifts. Content may repaint without moving, and a moving element can be displaced by a different element. The highlight alone does not identify scripting cost, layout cost or how much work occurred on a particular frame.

Record the same task in the Performance panel and inspect the relevant frames. Compare the interaction before and after a targeted change using the same environment. Avoid publishing a percentage improvement from one noisy recording or from differently sized pages.

Keep only a justified repair

  • Confirm the visible output and interaction still match the requirement.
  • Repeat the recording with the suspected change enabled and disabled.
  • Check a representative slower device when the task warrants it.
  • Inspect nearby overlays and sticky content after rendering-related changes.
  • Disable diagnostic overlays before reviewing final visuals.

Do not respond to every flash by adding will-change or forcing a new layer. Those changes can consume resources and alter stacking behavior. Use the measured will-change workflow only when evidence supports it. A useful report names the exact trigger, affected region, observed timing and tradeoff, rather than labeling all repainting as a defect.
