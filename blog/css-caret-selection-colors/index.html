Review Caret and Text Selection Colors in Form Fields

Distinguish the insertion caret, selected text and keyboard focus indicator. Test authored colors across field surfaces, themes and user preferences.

By Penta AIPublished 15 November 20262 min read

In this guide

  1. Keep the text-editing states distinct
  2. Inspect the interaction that reveals each state
  3. Check themes and user preferences

Caret-color changes the text insertion caret. The ::selection pseudo-element styles selected text. Neither replaces a keyboard focus indicator around the control. Review all three states separately when customizing an editor or input field.

Keep the text-editing states distinct

.notes {
  color: #17263d;
  background: #fff;
  caret-color: #174fa0;
}
.notes::selection {
  color: #102846;
  background-color: #c8defb;
}
.notes:focus-visible {
  outline: 3px solid #174fa0;
  outline-offset: 3px;
}

These colors are an original starting example for a white field, not a completed theme audit. Check the actual field surface, selected text and adjacent content. A caret that looks clear in a white editor may disappear in a local dark surface if the color is inherited or reused carelessly.

Reference: MDN caret-color reference.

Reference: MDN ::selection reference.

Inspect the interaction that reveals each state

Click between two characters to locate the insertion caret, then select a word to inspect the selection treatment. Tab to the field to review keyboard focus. A screenshot of an unfocused empty field cannot demonstrate any of those states.

Caret-color: auto lets the browser choose the caret color, commonly based on the current text color. An explicit brand color is optional. Avoid transparent carets in editable content unless a fully reviewed alternative editing interface supplies the necessary feedback.

Selection styling supports only a limited set of properties and follows highlight-specific inheritance behavior. If a rule appears ineffective, check property support and selector scope before increasing specificity. Native field selection also deserves testing across browsers rather than assuming a paragraph specimen proves input behavior.

Check themes and user preferences

  • Select short and long text in each supported field surface.
  • Move the caret with arrow keys and verify its location remains visible.
  • Test light, dark and forced-colors environments.
  • Review disabled and read-only fields without implying they share editable behavior.
  • Check enlarged text and high-density displays.

Do not disable system color adjustments just to preserve a custom selection palette. Keep the user’s ability to locate and read text as the goal. Use the contrast workflow for relevant foreground/background pairs, and document caret, selection and focus as separate states in the field specification.
