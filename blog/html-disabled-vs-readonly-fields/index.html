disabled vs readonly: Choose the Right Form Behavior

Compare focus, editing and submission for unavailable form fields. Keep read-only values available when needed and verify what the server actually receives.

By Penta AIPublished 30 October 20262 min read

In this guide

  1. Compare two labeled text fields
  2. Match the attribute to the control type
  3. Test the intended task

Use readonly when a supported field should remain available for reading and copying but not editing. Use disabled when a control is unavailable. The difference affects focus and form submission, not just styling, so replacing one with the other can change the data the application receives.

Compare two labeled text fields

<form>
  <label for="reference">Reference code</label>
  <input id="reference" name="reference" value="SAMPLE-042" readonly>

  <label for="coupon">Coupon code — unavailable for this order</label>
  <input id="coupon" name="coupon" value="" disabled>
</form>

The reference is sample data. The read-only field can normally receive focus and its named value is included in form data. The disabled field is excluded. Test the actual form serialization rather than assuming both visible values are submitted.

Reference: MDN: readonly.

Reference: MDN: disabled.

Match the attribute to the control type

readonly applies to supported textual inputs and textarea, not to every form control. Adding it to a select or checkbox does not create a read-only version of that control. If someone only needs to see a final value, ordinary text may be a clearer representation than an inactive control.

Both attributes are Boolean: writing disabled="false" still leaves the attribute present and therefore active. Use the DOM property or remove the attribute to change the state. Review constraint validation as well; these states are not equivalent to an editable required field.

Test the intended task

  • Tab through the form and verify which fields can receive focus.
  • Try copying a reference value with the keyboard.
  • Inspect submitted FormData in a controlled test.
  • Enable an unavailable control and confirm its value and validation behavior.

Explain why an important control is unavailable using visible supporting text, especially when it cannot receive focus to reveal help. Neither attribute is an authorization boundary: submitted values can be altered outside the normal interface. The server must validate what it accepts. Document the display state, editability, focus behavior and submission rule together so the visual treatment does not conceal a data-flow change.
