Build Dark Mode with Semantic CSS Color Tokens

Create light and dark themes with semantic CSS variables. Respect system preferences, distinguish color-scheme, and test surfaces, controls and contrast.

By Penta AIPublished 26 October 20263 min read

In this guide

  1. Define roles before shades
  2. Implement a system-preference version
  3. Review assets and elevated surfaces
  4. Audit pairs and states in each theme
  5. Document the theme contract

Build dark mode by assigning new values to semantic color roles, not by inverting the finished page. Text, surfaces, borders and actions have different jobs. A role-based theme lets a component keep its meaning while its values change between light and dark contexts.

Start with one complete component and its surrounding page surface. Include a label, secondary text, a button, a border and a focus state. Testing only a blank dark canvas misses most of the decisions that make a theme usable.

Define roles before shades

RoleQuestion to answer
Page surfaceWhat sits behind the main content?
Raised surfaceHow does a card separate from the page?
Primary textWhat color carries the main reading content?
Secondary textDoes supporting copy remain readable?
Action and focusHow are interaction and keyboard position visible?

Avoid naming a role after its current appearance, such as white-card, when that appearance will change. A name such as surface-card survives both themes. Keep brand accents separate from text-on-accent colors; a brand color does not guarantee that either white or black text will pass contrast.

Implement a system-preference version

:root {
  color-scheme: light;
  --surface-page: #f5f5f5;
  --surface-card: #ffffff;
  --text-primary: #17191c;
  --text-secondary: #4a4a52;
  --border-card: #d6d5d7;
}
@media (prefers-color-scheme: dark) {
  :root {
    color-scheme: dark;
    --surface-page: #101013;
    --surface-card: #1c1c21;
    --text-primary: #f4f4ee;
    --text-secondary: #c4c4cc;
    --border-card: #45454e;
  }
}
body { background: var(--surface-page); color: var(--text-primary); }
.card {
  background: var(--surface-card);
  border: 1px solid var(--border-card);
}
.caption { color: var(--text-secondary); }

The prefers-color-scheme media feature detects the user’s requested theme. The separate color-scheme property informs browser-provided rendering such as form controls and scrollbars. It does not automatically redesign every authored element.

This example follows the system preference only. A user-selectable light, dark and system control requires additional state and precedence rules. If you add one, make the explicit choice override the system setting and decide how that choice persists. Do not describe a system-only media query as a complete theme toggle.

Review assets and elevated surfaces

A transparent logo that looks clear on white may disappear on a dark card. Test logos, charts and illustrations against their actual destination surfaces. For complex images, provide an intentional background or a suitable alternate asset instead of applying a blanket inversion filter.

Shadows also need review. Increasing black shadow opacity on a nearly black background may provide little useful separation. A lighter card surface, border or different elevation treatment can be more effective. The shadow inspection guide shows how to separate those effects.

Audit pairs and states in each theme

Check primary and secondary text, link text, selected items, focus indicators, validation errors and disabled controls. Use the contrast workflow for the relevant pairs. Do not assume the light theme’s results apply after replacing token values.

Also inspect content inside embedded widgets and dialogs. A component that defines its own surface but inherits an unexpected text color can produce a mismatch. Trace local token overrides and keep the foreground/background pair together when a component creates a new visual context.

Document the theme contract

Deliver a side-by-side component sheet and the semantic token map. Record any assets that need variants and any states that intentionally use different treatment. Test a fresh load as well as preference changes. A maintainable dark theme is a set of reviewed relationships, not simply a second list of hex codes.
