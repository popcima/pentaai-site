Choose tabindex Zero or Minus One for the Intended Focus Path

Distinguish sequential keyboard focus from programmatic focus. Use native controls first and avoid positive tabindex values that create a separate ordering system.

By Penta AIPublished 18 November 20261 min read

In this guide

  1. Give a programmatic destination a narrow purpose
  2. Preserve native interaction semantics
  3. Walk both paths

Tabindex zero generally adds an element to sequential keyboard navigation in document order. A negative value lets a focusable target receive programmatic focus without becoming an ordinary Tab stop. Choose based on the interaction, rather than adding tabindex to every visible wrapper.

Give a programmatic destination a narrow purpose

<h2 id="review-summary" tabindex="-1">Review summary</h2>
<button type="button" id="show-summary">Go to review summary</button>
document.querySelector('#show-summary').addEventListener('click', () => {
  document.querySelector('#review-summary').focus();
});

The heading can receive focus when the user activates the dedicated action. It does not become an extra stop during ordinary Tab navigation. Verify the resulting focus indicator and viewport position in the complete page, not only by reading the attribute.

Reference: MDN tabindex.

Preserve native interaction semantics

A button or link already has keyboard behavior appropriate to its element. Adding tabindex to a generic div does not supply button activation, an accessible role or disabled behavior. Use the native element unless the application has a specific reason and a complete custom interaction implementation.

Positive tabindex values introduce priority ordering before ordinary zero and native focus stops. This can diverge from reading order as content changes. Fix document structure instead of assigning increasing numbers to reproduce a visual layout. A negative tabindex is also not a way to disable an action or hide it from assistive technology.

Walk both paths

  • Tab forward and backward through the component.
  • Activate the action that moves focus programmatically.
  • Confirm the active element and visible focus treatment.
  • Repeat after conditional content is inserted or removed.

Keep focus movement connected to an understandable user task. A noninteractive heading does not need focusability simply because it is visually prominent. For a route change, modal or composite widget, follow the interaction pattern’s complete focus requirements rather than applying this small example universally.

Use the visual-order review when the tab sequence feels wrong. Use focus without automatic scrolling only when the destination’s visibility is already handled deliberately.
