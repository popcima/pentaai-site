Clear Stale Errors in the Constraint Validation API

Use setCustomValidity for a real rule and clear it when the value changes. Distinguish validity checks from reporting and preserve server-side validation.

By Penta AIPublished 16 November 20262 min read

In this guide

  1. Clear the old message before rechecking the rule
  2. Choose when to inspect and when to report
  3. Review the full recovery sequence

A nonempty setCustomValidity message keeps a control invalid until you clear it. If a corrected field still refuses submission, inspect whether an earlier custom error remains set. Native validity rules and custom messages need a consistent update path.

Clear the old message before rechecking the rule

const code = document.querySelector("#reference-code");
function validateReference() {
  code.setCustomValidity("");
  if (code.value && !code.value.startsWith("REV-")) {
    code.setCustomValidity("Start the reference with REV-.");
  }
}
code.addEventListener("input", validateReference);

This example assumes a labeled text input and a real application rule requiring the prefix. Empty values are left to a required attribute if the field is mandatory. Clearing the message first prevents a previously invalid value from carrying a stale custom error into a corrected state.

Reference: MDN constraint validation guide.

Choose when to inspect and when to report

checkValidity() evaluates whether the control or form satisfies its constraints and returns a result. reportValidity() also asks the browser to report a problem to the user. Repeatedly reporting on every keystroke can be disruptive; choose a deliberate validation moment such as a relevant action or submission attempt.

Run your rule for every path that changes the value, including application code that sets a field programmatically. The input event handler only covers the events it actually receives. If a custom rule depends on another field, changing that dependency must also trigger revalidation.

Do not rely exclusively on a submit event handler to clear a stale custom error: native validation can prevent the submit event from firing. Keep custom state current before the browser reaches that submission check.

Review the full recovery sequence

  • Enter an invalid value and trigger the intended validation action.
  • Correct it and confirm the custom error is cleared.
  • Set the value through the application’s restore or autofill path.
  • Change any dependent field and recheck the result.
  • Test a server rejection while preserving the user’s other entries.

The browser’s validity state is not a substitute for server validation or persistent, accessible error text. Follow the form-error workflow for field associations and correction advice. Document both the rule and when it runs, so later UI changes do not leave a hidden stale validity state behind.
