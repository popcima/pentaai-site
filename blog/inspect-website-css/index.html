How to Inspect CSS on a Website with Chrome DevTools

Find the CSS behind any page element, understand computed styles, and check layouts, hover states, and responsive behavior in Chrome DevTools.

By Penta AIPublished 25 October 20264 min read

In this guide

  1. 1. Select the element that owns the appearance
  2. 2. Separate authored rules from computed values
  3. 3. Inspect the parent layout and box model
  4. 4. Check hover, focus, and content changes
  5. 5. Compare wide and narrow screens
  6. 6. Rebuild the smallest useful example
  7. 7. Save decisions, not a property dump

To inspect CSS on a website, right-click the element and choose Inspect. In Chrome DevTools, use Styles to trace the rules that affect it and Computed to check the resulting values. Then inspect the parent layout, interactive states, and narrower screens before treating those values as a reusable component.

A useful inspection answers a specific question: why does this card have this width, where does this text color come from, or what makes this button change on focus? Start with one question and follow the evidence. Copying every property usually gives you a larger pile of CSS without explaining the design.

1. Select the element that owns the appearance

Right-click directly on the visible text, border, or image you want to understand. Check the selected node in the Elements panel. A click on a label may select a nested span even though the surrounding button owns its background, border, and padding.

Move between that node and its parent while watching the page highlight. For a card, inspect the outer container for spacing, the heading for typography, and the image for cropping. Record which element owns each decision. That small distinction makes your eventual implementation easier to maintain.

2. Separate authored rules from computed values

The Styles panel includes matching rules, including declarations that lose in the cascade. Computed gives you the values applied to the selected element. Filter by a property such as color and follow its source when you need to understand an override. Chrome documents both panels in its CSS features reference.

For an original example, imagine these two rules in your own stylesheet:

.card { color: #24332a; padding: 1.5rem; }
.featured .card { color: #102317; }

A card inside a container with the featured class gets the second color. The first rule still matters because it supplies the padding. Copying only the last rule would lose part of the component; copying both without their context would preserve a dependency you may not want.

Also record the authored unit where useful. A displayed pixel value can be the current result of a relative unit, a variable, or a calculation. The result is evidence of this rendering, not a complete account of the original design decision. MDN describes this distinction in the getComputedStyle reference.

3. Inspect the parent layout and box model

When an element seems too wide or incorrectly positioned, move outward. Look for the parent’s display mode, available width, alignment, and gap before changing the child’s margin. A consistent gap between siblings often belongs to their shared container.

Use the box-model diagram to distinguish content size from padding, borders, and margins. With box-sizing: border-box, the declared width includes padding and borders. MDN’s box-sizing reference explains the sizing models. For grids, Chrome’s grid overlay exposes tracks and lines, helping you distinguish a layout rule from coincidental alignment.

4. Check hover, focus, and content changes

Use the :hov control in Styles to force a relevant pseudo-class, such as hover or focus. Inspect any changed color, outline, shadow, or transform. Then use the keyboard on the actual page: a forced visual state does not tell you whether the interaction is usable.

For your own component, replace a short label with a longer one and increase the content length. Does the button wrap gracefully? Does the card expand? Record behavior alongside measurements. “The card grows with its content” is more useful than carrying over a fixed height measured from one short paragraph.

5. Compare wide and narrow screens

Open the device toolbar and use a responsive viewport. Resize gradually so you can see when the layout changes instead of testing only one phone preset. Chrome’s device mode guide explains the controls and notes that simulation is an approximation of a real mobile device.

Compare the same element at both widths. Record changes to columns, horizontal padding, text wrapping, and navigation. If you see a media query in Styles, keep its condition with your notes. If the layout simply flows into available space, avoid inventing a breakpoint that the evidence does not support.

6. Rebuild the smallest useful example

Turn the observations into a small component in your own project. Here is an original starting point for a flexible card, using deliberate example values rather than a copied site’s stylesheet:

.card {
  box-sizing: border-box;
  width: min(100%, 36rem);
  padding: 1.5rem;
  border: 1px solid #d9e3dc;
  border-radius: 1rem;
  color: #24332a;
  background: #f8faf8;
}
.card h2 { margin: 0 0 .75rem; }
.card p { margin: 0; line-height: 1.6; }

Compare this component with your notes, then add only the missing behavior. Use the font inspection guide for typography and the color palette workflow for reusable color roles.

7. Save decisions, not a property dump

Your final notes should name the component, its purpose, the source page, viewport, state, and properties that matter. Separate confirmed values from assumptions. A single screen cannot reveal every component variant or the rules used across an entire product.

For a broader audit, continue with extracting a design system from a website. Keep inspection evidence, implementation choices, and unresolved questions distinct so another developer can reproduce your reasoning.
