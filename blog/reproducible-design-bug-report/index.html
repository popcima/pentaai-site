Write a Design Bug Report a Developer Can Reproduce

Turn a visual mismatch into a useful report with a trigger, environment and expected behavior. Separate observed evidence from a proposed CSS fix.

By Penta AIPublished 16 November 20262 min read

In this guide

  1. Describe the trigger and the result
  2. Attach evidence that explains ownership
  3. Give the repair a verifiable finish line

A useful design bug report lets another person reproduce the same mismatch without guessing the page state or viewport. Start with the task that fails, then provide the smallest set of conditions that makes the defect appear. A screenshot supports that record but rarely replaces it.

Describe the trigger and the result

Page: /review/example
State: export panel open; long file name selected
Viewport: 360 × 800 CSS pixels
Browser and zoom: record the tested version and setting
Steps: open panel, select sample, Tab to the final action
Observed: the action label is clipped on its second line
Expected: the complete label remains visible and operable

This is a hypothetical report template, not a claim about Penta AI. Replace every field with what you observed. Include the content string that triggers wrapping, using safe specimen data instead of private account details.

Attach evidence that explains ownership

Capture the full affected component and enough surrounding layout to show the relationship. If the child seems too wide, inspect its parent’s layout and box model. Note the element that owns the relevant height, overflow or spacing rule, rather than attaching a large unsorted dump of CSS.

Reference: Chrome DevTools CSS inspection reference.

Separate observation from a proposed repair. “The second line is clipped when this panel is 360px wide” is evidence. “Remove height: 40px” is a hypothesis until you test long labels, neighboring elements and alternate states. A developer may find a better fix once the underlying constraint is clear.

If the issue appears only after loading, record the timing and request conditions. If a pseudo-class was forced in DevTools, say so. Include browser zoom and the screenshot capture conditions so an exported image’s dimensions do not become an accidental layout specification.

Give the repair a verifiable finish line

  • Specify the affected task and the expected usable result.
  • Include one failing fixture and one ordinary case that must still work.
  • List important states such as error, loading, focus and long content.
  • Record whether the problem occurs on real hardware or in emulation.
  • Retest the original sequence after the proposed fix.

Keep unrelated visual opinions in separate issues so one repair has a clear purpose. A concise report with a reproducible trigger is more actionable than a gallery of unlabeled screenshots. Use the handoff checklist for the broader specification, and use this report to isolate a particular failure against it.
