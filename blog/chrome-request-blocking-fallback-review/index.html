Test Missing Resources with Chrome Request Conditions

Block one image, font or request to review a page’s fallback behavior. Keep patterns narrow, verify the blocked request and restore normal loading afterward.

By Penta AIPublished 16 November 20262 min read

In this guide

  1. Block a specific request and confirm the simulation
  2. Review the fallback against the user’s task
  3. Restore and compare

Use Chrome DevTools’ request-blocking controls to test how your own page behaves when a resource fails to load. Block one known image, font or request at a time so the resulting fallback has an explainable cause. A simulated failure is useful evidence when it is labeled and reproducible.

Block a specific request and confirm the simulation

  • Open Network and reload to locate the resource.
  • Use the request’s context menu to block it, or add a narrow pattern in Request conditions.
  • Keep blocking enabled and reload the relevant page state.
  • Check the request status to confirm DevTools actually blocked it.

Reference: Chrome DevTools Request conditions documentation.

Chrome’s current documentation calls the drawer Request conditions; older installations may use request-blocking wording. A status such as blocked:devtools distinguishes the simulation from a real server failure. Record the exact pattern rather than reporting that “the image server is down.”

Review the fallback against the user’s task

For an image, check alternative text, reserved layout space and whether an essential action remains understandable. For a web font, inspect fallback text, wrapping and button sizes. For a data request, verify that a useful error or retry path appears instead of a permanent spinner.

Blocking an entire domain can also block unrelated assets and authentication flows, making the result harder to interpret. Start with the smallest resource that answers the question. If caching or a service worker means the resource is not requested again, inspect the actual loading path before claiming the test passed.

Do this in a safe review context with representative data. A failed-request test should not require submitting a destructive production action. Keep the simulated condition separate from ordinary browsing and from any real incident report.

Restore and compare

  • Disable the pattern and reload to confirm the normal state returns.
  • Check that the fallback did not erase useful user input.
  • Repeat with another resource only after recording the first result.
  • Verify that images, fonts and data requests need different recovery strategies.
  • Remove or disable diagnostic patterns when the review ends.

DevTools can retain saved patterns even after a session ends, so explicitly inspect them during later debugging. Use the font-loading guide or the alternative-text workflow for the corresponding repair. A good fallback keeps the task understandable, not merely free of console errors.
