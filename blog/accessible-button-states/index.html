Accessible Button States: Default, Focus and Disabled

Specify buttons beyond the default screenshot. Cover keyboard focus, hover, pressed and disabled behavior with native HTML and a practical review matrix.

By Penta AIPublished 26 October 20263 min read

In this guide

  1. Specify states separately
  2. Build from a native control
  3. Choose disabled behavior intentionally
  4. Account for work in progress
  5. Run the interaction check

An accessible button specification includes its purpose, label, keyboard behavior and states, not only its default appearance. Begin with a native button for an action and define what happens before, during and after activation. A link remains the appropriate element when the primary purpose is navigation.

Use a small review matrix for every important action. The matrix turns vague feedback such as “make it accessible” into concrete checks that a designer and developer can perform on the same component.

Specify states separately

StateWhat to define
DefaultLabel, dimensions, colors and action
HoverPointer feedback without hiding essential information
Keyboard focusPersistent visible indicator and clear location
PressedFeedback while activation occurs
DisabledWhy the action is unavailable and how it behaves
Busy or completedProgress, duplicate-action handling and result feedback

The ARIA button pattern documents button semantics and keyboard expectations. Native HTML supplies much of this behavior; replacing a button with a clickable generic element creates more work and more ways to miss an interaction.

Build from a native control

<button class="action" type="button">
  Save changes
</button>
.action {
  min-height: 2.75rem;
  padding: .65rem 1rem;
  border: 1px solid transparent;
  border-radius: .75rem;
  background: #183224;
  color: #ffffff;
  font: inherit;
}
.action:hover:not(:disabled) { background: #244b35; }
.action:focus-visible {
  outline: 3px solid #155eef;
  outline-offset: 3px;
}
.action:disabled { opacity: .6; }

This is an illustrative starting point, not a complete component library. Test the outline against every adjacent surface and confirm that ancestors do not clip it. The focus-visible criterion explains why sighted keyboard users need to know where interaction will occur.

The example’s height is a design choice. WCAG 2.2’s minimum target-size criterion generally uses 24 by 24 CSS pixels, with specified exceptions including spacing. Do not treat a tiny visible icon as the whole target when a larger button box can make the action easier to use.

Choose disabled behavior intentionally

A native disabled button suppresses activation and is normally removed from sequential keyboard focus. If users need to understand why the action is unavailable, provide a visible explanation near the relevant controls. A tooltip available only on hover is a weak place for essential instructions.

Using aria-disabled="true" communicates a disabled state but does not itself suppress activation or apply visual treatment. MDN’s aria-disabled reference explains the implementation responsibilities. Choose that pattern only when you deliberately need its behavior, then guard mouse and keyboard activation in code.

Account for work in progress

For an asynchronous save, decide whether repeated activation should be prevented, which label appears during the request and where success or failure is communicated. Preserve enough context for a user to understand what changed. If the request fails, make the retry path available and explain the problem near the relevant interface.

A spinner alone is not a complete status message. Keep the action’s meaning clear and consider how updates are announced to assistive technology. Avoid replacing a concise label with a symbol that only makes sense to someone watching the animation.

Run the interaction check

Tab to the button, activate it with the expected keyboard inputs, and follow the resulting focus behavior. Repeat with a long label, enlarged text and the dark theme. Confirm that a disabled action cannot be triggered through another input path.

Finally, review label contrast and focus visibility using the contrast guide. Save the state matrix beside the component examples. That record gives later edits a clear standard for preserving behavior as well as appearance.
