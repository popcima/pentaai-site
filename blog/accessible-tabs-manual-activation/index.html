Review Accessible Tabs with Manual Activation

Audit a manual-activation tab interface. Separate keyboard focus from selection and check tab roles, panel relationships, arrow keys and content access.

By Penta AIPublished 27 October 20262 min read

In this guide

  1. Write down the state model
  2. Run a keyboard sequence
  3. Inspect what changes on activation

In manually activated tabs, arrow keys move between tab labels while Enter or Space selects a tab and reveals its panel. Focus and selection are separate states. This is useful when switching panels is expensive or delayed, because exploring the labels does not need to start every panel transition.

Write down the state model

<div role="tablist" aria-label="Project information">
  <button id="tab-overview" role="tab" aria-selected="true"
    aria-controls="panel-overview" tabindex="0">Overview</button>
  <button id="tab-files" role="tab" aria-selected="false"
    aria-controls="panel-files" tabindex="-1">Files</button>
</div>
<section id="panel-overview" role="tabpanel"
  aria-labelledby="tab-overview" tabindex="0">Project overview.</section>
<section id="panel-files" role="tabpanel"
  aria-labelledby="tab-files" tabindex="0" hidden>Project files.</section>

This markup is a state specimen for review, not a complete tabs implementation. It needs keyboard and activation logic. Do not ship the roles alone and assume native buttons provide arrow-key navigation. These example panels start with plain text, so they are focusable; a panel beginning with an appropriate focusable element can use a different entry strategy.

Reference: WAI-ARIA APG: tabs pattern.

Run a keyboard sequence

  • Tab into the widget: focus should arrive on its active tab.
  • Press Right Arrow: focus moves to the next label without changing the displayed panel.
  • Press Enter or Space: selection moves, the old panel hides and the new one appears.
  • Press Tab: leave the tab list and reach the active panel or its meaningful first control.
  • Check wraparound at the first and last tabs; test Home and End if provided.

For a horizontal tab list, do not capture Up and Down simply because the script already handles other arrows. Those keys normally remain available for page scrolling. Review vertical tabs against their corresponding keyboard model instead of copying a horizontal handler unchanged.

Inspect what changes on activation

Compare aria-selected, tabindex, hidden panels and the visible selection indicator before and after the action. The selected tab must reference the correct panel, and that panel must reference its label. A focus ring should remain distinguishable from the selected-state treatment; a screenshot where both look identical can hide an interaction bug.

Use two deliberately different panel contents during testing, such as a short overview and a long file list. Confirm that hidden controls cannot receive focus, repeated IDs do not appear when a second widget is added, and loading states do not leave selection pointing at stale content. For production code, start from a reviewed implementation and test it with your actual content and supported assistive technologies.
