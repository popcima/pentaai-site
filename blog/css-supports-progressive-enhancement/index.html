Build a Useful CSS Fallback with @supports

Use feature queries to layer a CSS enhancement onto a usable baseline. Test both paths and distinguish syntax support from a verified accessible interaction.

By Penta AIPublished 30 October 20261 min read

In this guide

  1. Enhance an already readable title
  2. Query the feature that changes the design
  3. Review both versions as real states

A feature query lets a stylesheet apply an enhancement when the browser accepts a particular CSS feature. Start with a usable baseline outside the query, then add the optional behavior inside. This makes the unsupported path an intentional design rather than an accidental pile of missing declarations.

Enhance an already readable title

.article-heading {
  max-inline-size: 24ch;
  line-height: 1.15;
}
@supports (text-wrap: balance) {
  .article-heading { text-wrap: balance; }
}

The heading still wraps and remains readable without balancing. The enhanced path changes the distribution of words across lines. Neither path depends on a fixed heading height, so a longer title can grow normally.

Reference: MDN: @supports feature queries.

Query the feature that changes the design

A browser accepting one property does not prove that a separate selector or API is available. Selector queries use selector(), for example @supports selector(:has(input:checked)). Keep the test close to the behavior you are enabling. A support result is about accepted syntax, not a full compatibility or accessibility test.

@supports selector(:has(input:checked)) {
  .option:has(input:checked) { border-color: #174fa0; }
}

This second specimen only adds a visual cue. A checked native input and its label should remain understandable without the cue. Do not hide essential instructions outside the supported path and expect the feature query to supply missing semantics.

Review both versions as real states

  • Temporarily disable the enhancement block and inspect the baseline.
  • Try the longest content and the smallest supported width.
  • Check forced colors and keyboard focus independently.
  • Use a supported older browser when the fallback is part of your compatibility promise.

If two layout features must work together, an and condition can express that dependency. Keep the conditional block focused so a later reader can identify what is being tested. In handoff notes, show the baseline and enhanced appearance with the same content; documenting only the enhanced screenshot leaves the most important fallback decision unresolved.
