CSS Variable Fallbacks: Missing Values vs Invalid Values

Debug CSS custom properties by tracing scope, inheritance and var fallbacks. Learn why an existing value of the wrong type can still break a declaration.

By Penta AIPublished 26 October 20263 min read

In this guide

  1. Start with a missing token
  2. Compare a value of the wrong type
  3. Trace scope and spelling
  4. Use registration when a typed token helps
  5. Make the token contract explicit

A var() fallback helps when the referenced custom property is missing or has an invalid custom-property value. It does not validate every value against the property where you use it. If --text-color exists but contains 20px, inserting it into color can invalidate the declaration instead of choosing your fallback color.

When a token appears to do nothing, inspect the consuming property and then follow the custom property through its scope. This is more reliable than repeatedly adding fallback arguments without checking which value the browser receives.

Start with a missing token

.notice {
  color: var(--notice-text, #243449);
  background: var(--notice-surface, #edf3fa);
}

In this unregistered-variable example, absent notice tokens allow the supplied values to be used. The fallback belongs to that individual use of the variable; it does not define the token for other components. If several components need the same default, a declaration on an appropriate shared ancestor may be easier to maintain.

Compare a value of the wrong type

.example {
  --text-color: 20px;
  color: var(--text-color, #243449);
}

The custom property exists, so the fallback is not selected merely because 20px is unsuitable as a color. After substitution, the color declaration is invalid at computed-value time. For an inherited property such as color, that can result in inherited color rather than the earlier declaration you expected. MDN explains this distinction in its custom properties guide.

SymptomCheck first
Fallback appears unexpectedlyIs the token in scope on this element?
Neither intended value nor fallback appearsIs the substituted value valid for the consuming property?
Child differs from parentIs there a local override or registration changing inheritance?
Only one theme breaksDoes that theme define every required semantic token?

Trace scope and spelling

Custom-property names are case-sensitive. Compare the exact name in the definition and use, including prefixes. Next inspect the selected element’s ancestors and any local override. A token defined inside a sibling component is not a global variable for the rest of the document.

In DevTools, expand the consuming property and follow the value to its declaration. Temporarily replace the variable with a known valid literal. If the property still does not take effect, return to the cascade debugging guide; the variable may not be the cause.

Use registration when a typed token helps

@property --notice-text {
  syntax: "<color>";
  inherits: true;
  initial-value: #243449;
}

Registration declares a type, an inheritance rule and an initial value. This changes how the token behaves compared with an unregistered custom property. The property registration reference describes the required descriptors and validity conditions. Check support in your target browsers before depending on registered behavior.

Choose inherits deliberately. Theme tokens often need to flow to descendants, while a component’s internal animated value might not. Do not copy a registration with inheritance disabled into a theme system and then assume every child receives the parent’s override.

Make the token contract explicit

Document the expected type, where the token is defined, whether it inherits and which components consume it. For a color role, include the paired surface rather than only a hex value. For a spacing role, state whether percentages are permitted or whether it should always be a length.

Test the normal value, a missing value and a deliberately incorrect value in a small local example. Those three cases reveal different failure modes. Once the contract is clear, map the reviewed tokens into your framework using the Tailwind theme workflow rather than exporting an unexamined pile of custom properties.
