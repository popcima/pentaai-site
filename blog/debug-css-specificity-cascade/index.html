Why Your CSS Is Not Applying: Debug the Cascade

Find why a CSS declaration loses without adding random important flags. Trace selector matches, cascade layers, specificity, inheritance and source order.

By Penta AIPublished 26 October 20263 min read

In this guide

  1. Confirm the declaration can participate
  2. Read the cascade in the right order
  3. Reproduce a layered conflict
  4. Check inheritance separately
  5. Make the smallest durable repair

When CSS is not applying, inspect the winning declaration before making the selector more specific. Your rule might not match the element, might sit in an inactive media query, or might lose because of cascade layers or importance. Specificity is only one part of that decision.

Pick one property on one element: for example, the background of a primary button. Write down the expected value and the value shown in the Computed panel. This keeps a layout problem from becoming a general search through every stylesheet in the application.

Confirm the declaration can participate

In the Styles panel, look for your rule. If it is absent, confirm that the stylesheet loaded and the selector matches the selected element. If present but inactive, inspect its media or support condition. Check syntax warnings before assuming that the browser has ignored valid CSS.

A crossed-out declaration is useful evidence: another declaration won. Expand the property in Computed to trace its origin. If a shorthand is involved, inspect the corresponding longhand too. A later background declaration can reset details you set with a more specific-looking background property.

Read the cascade in the right order

MDN’s cascade explanation separates relevance, origin and importance, specificity, scoping proximity and order of appearance. Layer ordering also matters within an origin. Comparing selector weights before establishing which layer or importance level wins can lead to the wrong fix.

QuestionUseful evidence
Does the rule apply here?Selector match and active condition
Which precedence group wins?Origin, important flag and layer
Do selectors break the tie?Specificity of matching selectors
Is scope involved?Nearest applicable scope root
Is everything else equal?Order in the stylesheet

Reproduce a layered conflict

@layer components, overrides;

@layer components {
  .checkout .button.primary { background: navy; }
}
@layer overrides {
  .button { background: teal; }
}

For these normal author declarations, the later overrides layer wins even though its selector is less specific. Now imagine an unlayered normal .button rule elsewhere: unlayered normal styles take precedence over normal layered styles. Important declarations have different layer ordering, so do not extrapolate this example to every important rule.

The practical repair is often to put the intended override in the right place in the layer structure, rather than add an ID selector. Name layers once near the entry point and keep component ownership understandable. If a third-party library supplies styles, decide how it enters your cascade before fighting individual declarations.

Check inheritance separately

A color inherited from a parent is different from a declaration targeting the child. Even a highly specific parent rule does not automatically beat a rule applied directly to the child. Also check whether the property inherits at all. MDN’s specificity guide covers these distinctions.

For a concrete debugging note, record “child label has its own color rule” instead of “specificity too low.” That description points to the actual competing declaration. When a value comes from var(), follow the custom-property chain as a second step.

Make the smallest durable repair

Temporarily disable the winning declaration to confirm the diagnosis. Then change the source rule, layer placement or component API that should own the behavior. Re-enable the surrounding CSS and test another component using the same class. A local visual improvement can otherwise create an unintended global override.

Use !important only when its role is deliberate and documented, not as the first response to uncertainty. Save the final change in the project source; a successful edit in DevTools alone disappears when the page reloads. Check the default, focus and disabled variants before calling the component fixed.
