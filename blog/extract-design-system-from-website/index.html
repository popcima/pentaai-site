How to Extract a Design System from an Existing Website

Audit colors, typography, spacing, and component states on a live website. Build a useful token inventory while separating observations from assumptions.

By Penta AIPublished 25 October 20264 min read

In this guide

  1. Choose a representative sample
  2. Build an observation inventory
  3. Separate observations from inferred rules
  4. Turn repeated values into meaningful tokens
  5. Write component specifications alongside the tokens
  6. Make the handoff usable

To extract a design system from a website, inspect representative pages, record recurring styles, group those observations into named tokens, and verify them across components and states. The result is a reconstructed inventory. A live website alone cannot tell you all of the team’s original design decisions, component APIs, or unpublished guidelines.

Start with one useful deliverable: a token sheet plus a few component specifications. You can expand it once you know which rules repeat. Trying to collect every CSS declaration first usually produces more cleanup than insight.

Choose a representative sample

Select pages that exercise different layouts: a marketing page, an article or documentation page, a form, and a list or dashboard if one exists. Within each, inspect a heading, paragraph, link, button, field, card, and navigation item. Record unavailable components as missing evidence, not as invented styles.

Set a clear scope: the viewport, theme, signed-in state, and date. If you have only a homepage, say so. A homepage can provide a visual direction, but it is a weak basis for claiming a complete product design system.

Build an observation inventory

ColorsValue, alpha, role, paired backgroundText, buttons, alerts, menus
TypographyRendered family, weight, size, line heightHeadings, body, labels, forms
SpacingGap, padding, margin, container widthCards, sections, compact layouts
ShapeBorder widths, radii, shadowsButtons, cards, dialogs
BehaviorFocus, hover, error, disabled statesKeyboard and pointer interaction

Use the dedicated font identification and color palette extraction guides for those passes. Keeping each pass focused makes it easier to compare the same property across several components.

Separate observations from inferred rules

Imagine observing card padding of 16px, 24px, and 32px. You might propose an 8px spacing step, but those three observations do not prove the entire site follows it. A 20px button inset or a fluid section gap could be equally intentional.

Keep two columns: observed value and proposed token. Add a confidence note based on repeated evidence. This is an editorial working method, not a statistical score. For example:

Observation: 24px gap between cards on the listing page
Proposal: space.section-item = 24px
Evidence: repeated in two desktop lists
Open question: mobile list uses a different gap
Decision: keep responsive values separate for now

This record gives the next person a reason for the choice and a way to challenge it. A token name without evidence can turn a guess into a rule that nobody remembers making.

Turn repeated values into meaningful tokens

Separate raw values from intended roles. A raw color might be green.200; a role might be color.action.background. Components should use roles where the meaning is stable. Avoid a token named after a particular position, such as left-card-green, unless that location is the real design concept.

The Design Tokens Community Group format defines a JSON interchange structure with token types, values, and aliases. It is useful when tools need to exchange tokens; it does not automatically reconstruct component behavior from a rendered page.

For a smaller project, a reviewed CSS variable file may be sufficient. MDN’s custom properties guide explains how values can be referenced and scoped. Choose the export format your project will actually maintain.

Write component specifications alongside the tokens

A button needs more than a background token. Document its label style, horizontal and vertical padding, border, minimum dimensions, focus appearance, disabled treatment, and behavior with a long label. Note which details you observed and which you are choosing for your own implementation.

Use a deliberately small validation set: one button, one form field, one card, and a page header. Rebuild them with your token sheet, then compare at narrow and wide widths. When they diverge, inspect the rule responsible instead of adding unexplained magic numbers.

Our CSS inspection guide covers the difference between a declaration in a stylesheet and the resolved styles you see. That distinction matters when a flexible layout produces a pixel width that should not become a fixed token.

Make the handoff usable

Deliver the source URLs and capture conditions, the named token file, component notes, unresolved questions, and a short list of permitted assets. Keep proprietary logos, font files, and illustrations out of a redistribution bundle unless you have the rights to include them.

For Tailwind projects, continue with mapping the inventory into Tailwind v4. For an AI coding workflow, use the DESIGN.md template to explain the decisions and explicitly instruct your agent to read it. A good handoff preserves uncertainty and rationale as carefully as it preserves hex codes.
