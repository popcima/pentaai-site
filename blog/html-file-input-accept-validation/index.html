File Input accept Is a Hint, Not Upload Validation

Build a labeled native file picker with clear format and size instructions. Validate the real upload and test cancellation, replacement and server rejection.

By Penta AIPublished 15 November 20262 min read

In this guide

  1. State the upload contract beside the picker
  2. Inspect the selected file, not the displayed path
  3. Test more than the happy path

The accept attribute guides a file picker toward expected formats. It does not establish that an uploaded file is valid or safe. Keep a native file input with a clear label, explain the limits, and validate the actual file on the server as well as providing helpful client-side feedback.

State the upload contract beside the picker

<form action="/assets" method="post" enctype="multipart/form-data">
  <label for="reference-image">Reference image</label>
  <input id="reference-image" name="reference" type="file"
    accept="image/png,image/jpeg"
    aria-describedby="reference-help" required>
  <p id="reference-help">PNG or JPEG, up to 5 MB.</p>
  <button type="submit">Upload image</button>
</form>

The endpoint and 5 MB limit are example choices that your implementation must actually enforce. The form encoding allows a normal multipart upload. If an application replaces this flow with JavaScript, preserve the same labeling, validation and error-recovery requirements.

Reference: MDN file input reference.

Inspect the selected file, not the displayed path

Use the input’s files collection when code needs the selected File objects. Do not parse the displayed value as a reliable filesystem path. Browsers intentionally avoid exposing the user’s real local path, and a filename or extension alone does not establish the file’s actual contents.

A client-side size check can prevent an avoidable failed request, but the server must enforce its own limits and accepted formats. Keep errors specific: explain whether the file is too large, unsupported or could not be uploaded. Leave a clear route to select a different file.

Do not hide the native control with display: none and assume a decorative label provides a complete keyboard interaction. If customizing the appearance, verify the real picker remains operable and the selected filename or equivalent feedback remains available.

Test more than the happy path

  • Choose a valid image and verify the actual upload result.
  • Cancel the picker and confirm the previous state remains sensible.
  • Select a large file and an unsupported file.
  • Replace the selection and retry after a server rejection.
  • Use keyboard navigation and test the native picker on mobile.

Report success only after the application confirms the upload. A local preview proves that the browser can display a selected file, not that the server stored it. Use the status-message pattern for an accurate result and keep format instructions visible before the user opens the picker.
