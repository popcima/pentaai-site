Turn Website Design Tokens into a Tailwind CSS v4 Theme

Map inspected colors and radii into semantic CSS variables and a Tailwind v4 theme, with an original example and component validation checklist.

By Penta AIPublished 25 October 20264 min read

In this guide

  1. 1. Collect values with their context
  2. 2. Choose semantic roles before utility names
  3. 3. Define the project’s CSS variables
  4. 4. Map the roles into Tailwind v4
  5. 5. Add typography and spacing selectively
  6. 6. Verify the theme through real components
  7. 7. Document what the theme guarantees

To turn website design tokens into a Tailwind CSS v4 theme, first identify recurring values and their roles, then map the values you have chosen for your project into Tailwind’s theme namespaces. Use ordinary CSS custom properties for semantic roles and @theme inline when Tailwind theme variables reference those properties.

The mapping is the easy part. The harder decision is which inspected values deserve to become shared rules. A page can contain one-off decoration, inherited defaults, and old overrides. Promoting every value into a token makes the theme harder to understand.

1. Collect values with their context

Before writing theme code, make a small inventory. For each candidate, record the component, visual role, state, and viewport. A green button background and a green success message may share a value while serving different purposes. Keep those roles separate even if they start with identical colors.

ObservationCandidate roleWhat to verify
Main content backgroundsurfaceOther pages and themes
Primary body textinkText on every surface
Primary action backgroundaccentHover and focus states
Repeated card roundingpanel radiusSmall and large cards

These are proposed names for an original implementation, not claims about how the inspected website names its tokens. Use the design-system extraction workflow to collect a broader sample before committing to a shared theme.

2. Choose semantic roles before utility names

Raw values describe appearance. Semantic roles describe intended use. A primitive might be green-900; a role might be ink. The distinction lets a theme change its appearance without changing what a component asks for.

For this tutorial, we will invent a compact reading interface with four roles: page surface, body text, accent, and text on the accent. Our values are examples, not extracted measurements or a claim that one palette suits every product. Validate the combinations in your own layout before shipping.

If you also exchange tokens between design tools, keep the interchange format separate from your Tailwind implementation. The Design Tokens Community Group format describes a JSON-based exchange format. A CSS theme file is not automatically a conforming token export.

3. Define the project’s CSS variables

Start with ordinary variables so components written without Tailwind can use the same decisions. Use a prefix that belongs to your project and avoid exporting every incidental measurement from the reference page.

:root {
  --site-surface: #f7faf7;
  --site-ink: #183224;
  --site-accent: #b9e8c7;
  --site-on-accent: #183224;
  --site-panel-radius: 1rem;
}

[data-theme="dark"] {
  --site-surface: #101b14;
  --site-ink: #ecf5ee;
  --site-accent: #b9e8c7;
  --site-on-accent: #183224;
}

Here, the dark theme changes the reading surface and text but keeps the action pairing. That is an intentional example decision. Do not infer an unseen dark theme from a light page. If a project has no approved dark palette, record that as an open design task.

4. Map the roles into Tailwind v4

In a project already configured for Tailwind CSS v4, add the following to the CSS entry file. The --color-* namespace supplies color utilities, and --radius-* supplies rounding utilities. Tailwind’s theme documentation recommends inline for theme values that reference other variables.

@import "tailwindcss";

@theme inline {
  --color-surface: var(--site-surface);
  --color-ink: var(--site-ink);
  --color-accent: var(--site-accent);
  --color-on-accent: var(--site-on-accent);
  --radius-panel: var(--site-panel-radius);
}

Place @import "tailwindcss"; first in the combined CSS entry file, followed by the earlier :root and dark-theme definitions and the @theme inline block. Now a component can request semantic utilities:

<article class="rounded-panel bg-surface p-6 text-ink">
  <h2 class="text-2xl font-semibold">A useful starting point</h2>
  <p class="mt-3 leading-relaxed">A small theme with clear roles.</p>
  <a href="/guides/" class="mt-6 inline-flex rounded-panel
    bg-accent px-4 py-3 text-on-accent
    focus-visible:outline-2 focus-visible:outline-offset-4">
    Explore the guides
  </a>
</article>

The code assumes your build scans the file containing these classes. It is a Tailwind v4 example; copying it into a v3 configuration does not perform an upgrade.

5. Add typography and spacing selectively

Only add a custom font family after the font files and loading strategy are part of your project. A family name in CSS does not install the font. Similarly, inspect several text roles before deciding a measured size represents a shared type scale.

Keep Tailwind’s existing spacing utilities when they fit the design. If your inventory shows a consistent alternative rhythm, document why it is necessary before replacing a global spacing decision. A single unusual gap is usually better handled locally than by redefining an entire scale.

6. Verify the theme through real components

Build a page containing a heading, paragraph, link, button, card, and input. This small specimen reveals missing roles more quickly than a palette displayed on its own. Test keyboard focus, long content, narrower widths, and every supported theme.

Use the palette inspection guide to review actual foreground/background pairings. Do not approve a color because its swatch looks pleasant. Check where the color appears and what the reader must distinguish.

7. Document what the theme guarantees

For each semantic role, write one sentence explaining when to use it. Add a short list of deliberate exceptions and unresolved observations. This prevents the next contributor from creating a new shade every time a screenshot looks slightly different.

Include those decisions in a DESIGN.md brief for an AI coding workflow if your team uses one. The goal is a small, explainable theme that supports real components, with clear evidence for the decisions you carried forward.
