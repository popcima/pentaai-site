CSS Container Queries: Make Cards Fit Their Own Space

Build reusable cards that adapt to their container instead of the viewport. Set up containment, choose a useful breakpoint and debug queries that do not apply.

By Penta AIPublished 26 October 20262 min read

In this guide

  1. Give the query a separate container
  2. Choose the threshold from the content
  3. Debug a query that never activates
  4. Keep global preferences separate

Use a size container query when a component should respond to the space its parent gives it. A card in a sidebar can remain compact while the same card in the main column uses a horizontal layout, even though both appear in the same browser window. A viewport breakpoint alone cannot distinguish those two situations.

Start with a readable stacked card. The query should enhance that working layout when sufficient space becomes available. This makes the component easier to reuse and gives you a sensible baseline if a target environment does not support the enhancement.

Give the query a separate container

<div class="story-slot">
  <article class="story-card">
    <img src="/images/story.webp" width="640" height="360" alt="A studio workspace">
    <div><h2>Inside the studio</h2><p>Story summary goes here.</p></div>
  </article>
</div>
.story-slot { container: story / inline-size; }
.story-card { display: grid; gap: 1rem; }
.story-card img { width: 100%; height: auto; }
@container story (min-width: 34rem) {
  .story-card {
    grid-template-columns: 12rem minmax(0, 1fr);
    align-items: start;
  }
}

The wrapper establishes the named inline-size container, and the query styles its descendant card. Do not expect the card to query its own size simply because you put containment on that same element. MDN’s container query guide explains containment, names and size queries.

Choose the threshold from the content

The 34rem threshold is an example, not a device category. Narrow the card’s slot until the side-by-side layout becomes uncomfortable, then choose a threshold that preserves readable copy and a useful image. Repeat with a longer title before accepting the value.

PlacementExpected behavior
Narrow sidebarImage above the text
Wide main columnImage and text side by side
Wide window with a narrow nested slotStill stacked
Long title at the thresholdWraps without pushing the image out

This test distinguishes the new component rule from the page-level layout. The page decides how much space a slot receives; the card decides how to use it. Keep those responsibilities separate instead of adding a new viewport breakpoint for every place the card appears.

Debug a query that never activates

Inspect the wrapper’s actual width, its computed container properties and the query name. Then check that the target is a descendant of the intended container. A wide browser does not imply that a sidebar container has crossed the threshold.

If the wrapper becomes unexpectedly small, review the surrounding layout and intrinsic sizing. Containment affects sizing behavior, so it should not be added indiscriminately to every element. Give the slot a clear place in its parent grid or flex layout, and use the overflow checklist when content refuses to shrink.

Keep global preferences separate

A component width query is not a replacement for every media query. System color preferences, reduced motion and page-wide navigation changes have different scopes. Choose the query mechanism that describes the decision you are making.

Document one narrow and one wide card example in the handoff. Include the container name, the threshold and the reason the layout changes there. Test the component in two simultaneous placements before calling it reusable: that is the situation where container queries provide the clearest benefit.
