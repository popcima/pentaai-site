Accessible Names vs. Descriptions: Choose the Right ARIA

Keep a control’s short name separate from supporting instructions. Use native labels first, then connect concise descriptions and inspect the computed result.

By Penta AIPublished 15 November 20262 min read

In this guide

  1. Keep the name concise and the help separate
  2. Reference existing visible text deliberately
  3. Test concise text and dynamic states

An accessible name identifies a control; an accessible description adds supporting information. Use a native label when the element supports one. Use aria-labelledby to reference text that names an element, and aria-describedby for supplementary text that should not replace its short identity.

Keep the name concise and the help separate

<label for="project-name">Project name</label>
<input id="project-name" name="project"
  aria-describedby="project-help">
<p id="project-help">Use a name your team will recognize.</p>

The field’s name remains Project name. The help text supplies a separate description. Putting both sentences into the label would make the control’s repeated identity longer than necessary. Using only a placeholder would make the visible guidance disappear during entry.

Reference: MDN aria-describedby reference.

Reference existing visible text deliberately

<section aria-labelledby="review-heading">
  <h2 id="review-heading">Review settings</h2>
  <!-- Related settings -->
</section>

This separate example uses a visible heading to name a section. IDs must be unique, and references must resolve in the same document. If multiple IDs are listed, their order contributes to the resulting text, so review the complete computed name or description instead of only checking that an attribute exists.

Do not add aria-label to a control that already has a good visible label just to restate it differently. Competing naming sources can produce a name that no longer matches what sighted users see. During debugging, inspect which source actually wins in the browser’s accessibility properties.

Test concise text and dynamic states

  • Focus the control and inspect its computed name and description separately.
  • Check that each referenced ID points to the intended element.
  • Trigger validation and confirm any added description is still relevant.
  • Listen with a supported screen reader and review repeated announcements.
  • Check that visible users can also find essential instructions.

Descriptions are exposed as text; a large structured help document is not a good fit for a single long aria-describedby string. Keep nearby instructions concise and provide an ordinary way to read more detailed help. For an icon-only control, start with the accessible-text workflow and verify the final name rather than stacking attributes until an audit warning disappears.
