When to Preload a Web Font—and How to Verify It Helps

Preload a genuinely critical font with matching request settings. Check for duplicate downloads, unused hints and competition with other early page resources.

By Penta AIPublished 27 October 20262 min read

In this guide

  1. Match the hint to the actual face
  2. Record a baseline before adding hints
  3. Remove hints that no longer fit the page

Preload a font when it is needed early and normal discovery starts its request too late. Do not preload every font in the project. A hint spends bandwidth earlier; it is useful only if that earlier work helps the current page rather than competing with more important resources.

Match the hint to the actual face

<link rel="preload" href="/fonts/interface-regular.woff2"
  as="font" type="font/woff2" crossorigin>
@font-face {
  font-family: "Interface";
  src: url("/fonts/interface-regular.woff2") format("woff2");
  font-weight: 400;
  font-style: normal;
  font-display: swap;
}

The example assumes this regular face appears in the initial viewport. Both references point to the same file. The preload starts a fetch; the font-face rule and the text’s font-family still determine how the font is used. Keep the file’s actual weight and style descriptors accurate.

The MDN preload reference explains the request-matching role of as, type and crossorigin. Font requests use CORS behavior, so the crossorigin attribute matters even when the font URL is on the same origin.

Record a baseline before adding hints

Open the page with DevTools, disable cache for the controlled test and use the same network profile for both versions. Record when the font request begins, whether text is visible during loading and which face is actually rendered. Also note the major image and stylesheet requests that share the early loading period.

Before/after checkWhy it matters
Font request starts earlierShows whether discovery changed.
Only the intended file is requestedAvoids mismatched or duplicate work.
Font is used by initial contentAvoids wasting an early hint.
Important image timing remains acceptableChecks competition for bandwidth.
Warm navigation still worksCovers ordinary repeat visits.

Do not claim a speed improvement from request order alone. Compare the visible result and repeat the measurement under consistent conditions. A small timing difference from one run can be noise. Keep your findings specific to the page and device conditions tested.

Remove hints that no longer fit the page

A global header can preload a display font on pages that never use it. A redesign can change the hero from bold to regular while leaving the old hint behind. Review preloads when typography roles or page templates change. Browser warnings about unused preloads are evidence to investigate, not instructions to add more hints.

For a variable font or language subset, verify which exact file the browser selects for the initial text. Avoid preloading every possible subset “just in case.” Keep fallback and font-display behavior as separate decisions; fetching a face earlier does not guarantee that layout will remain stable when its metrics replace the fallback.

Document the page, face, reason for the hint and the before/after observation. That small record makes it easier to remove a preload later if its original benefit disappears.
