DESIGN.md: A Practical Design Brief for AI Coding

Use this DESIGN.md template to give an AI coding assistant clear design tokens, layout rules, component states, evidence, and review criteria.

By Penta AIPublished 25 October 20265 min read

In this guide

  1. 1. Define the job and the audience
  2. 2. Label evidence and assumptions
  3. 3. Start from this original template
  4. 4. Link implementation data instead of duplicating it
  5. 5. Ask the assistant to use the brief explicitly
  6. 6. Review the rendered result against the brief
  7. 7. Update decisions when the product changes

A DESIGN.md file can serve as a human-readable design brief for an AI coding assistant: describe the interface, list approved design decisions, link relevant assets, and define how the result will be checked. In this guide, the filename is a suggested project convention. Do not assume every coding assistant automatically discovers it or treats it as a standardized instruction file.

The file works best when you explicitly provide it to the assistant and keep it close to the code it describes. A screenshot supplies visual context; the written brief explains which details are intentional, which interactions matter, and where the assistant should ask instead of inventing an answer.

1. Define the job and the audience

Start with the page’s purpose, the reader’s task, and the action the interface supports. “Build an elegant dashboard” leaves too many decisions open. “Build a project list where a team lead can identify overdue work and open a project” provides a useful basis for layout and behavior.

Name the stack and relevant files. Specify whether to reuse existing components, extend a theme, or create a new page. This keeps the work connected to your application.

2. Label evidence and assumptions

When you inspect a reference, record the URL, the date, viewport, and state. Identify what you directly observed and what you chose for your own implementation. A measured heading size does not prove the reference uses that size everywhere.

The website design-system extraction guide provides a useful starting inventory. Carry unresolved questions into the brief. For example, “mobile menu not observed” gives the builder a real constraint; silently inventing a menu and presenting it as faithful does not.

3. Start from this original template

The following is a complete example brief for a fictional project directory. Replace its choices with your approved decisions. The sample paths, colors, and widths describe that fictional implementation; they are not observations about another website.

# Design brief: Project directory

## Purpose
Help a team lead scan active projects and open the right one.
Primary action: open a project.
Secondary action: filter by status.

## Scope and implementation
Use the existing application framework and routing.
Reuse the project's Button and TextField components.
Keep the current project-loading and authentication behavior.
Implement the directory page, empty state, and filter state.

## Evidence
This brief defines an original design, not a website replica.
Reference assets: use only approved files in /assets/projects/.
Unknown: whether archived projects need a separate route.
Ask before adding an archive flow.

## Visual roles
Surface: #f7faf7
Primary text: #183224
Accent: #b9e8c7
Text on accent: #183224
Panel radius: 1rem
Use the existing font family and spacing scale.
Treat these as proposed values until contrast is checked.

## Layout
Place the page heading before filters and results.
Use a readable centered container with generous side padding.
At narrow widths, stack controls without clipping labels.
Let project titles wrap; do not hide essential status text.

## Components and behavior
Project item: title, owner, status, updated date, open link.
Filters: clear label, selected state, reset control.
Empty results: explain that no projects match; offer reset.
Loading: preserve layout and announce progress appropriately.
Error: explain the failed action and offer a retry.

## Accessibility and content
Use semantic headings and native controls where appropriate.
All actions must work with a keyboard and visible focus.
Do not use color as the only status cue.
Use realistic sample titles; do not invent customer claims.

## Review criteria
No horizontal page overflow at 375px or 1280px width.
Long titles and empty results remain usable.
Filters change visible results and reset restores them.
Verify contrast and keyboard navigation.
Report what was tested and any remaining limitations.

4. Link implementation data instead of duplicating it

If your project already has a theme file, point to it and explain the roles that matter. Copying a large token table into Markdown creates two places to update. A brief should make the source of truth obvious, especially when a color or type scale changes.

For Tailwind projects, see the guide to mapping design tokens into Tailwind v4. For interchange between tools, the Design Tokens Community Group format defines a structured token representation. This suggested Markdown brief complements those files; it does not replace their syntax or validation.

5. Ask the assistant to use the brief explicitly

Here is an original prompt you can adapt after placing the brief in your project:

Read DESIGN.md and the existing page, theme, and component files before editing. Implement the project directory described in the brief using the current stack. List any conflicting requirements or missing decisions first. Reuse existing components where they meet the requirements. After implementation, check the stated widths, keyboard interactions, filter reset, empty results, and long titles. Report the files changed, the checks performed, and unresolved limitations.

Replace generic references with actual paths. Keep the work small enough to review: one complete page with real states is a useful starting point.

6. Review the rendered result against the brief

Compare the implementation with the decisions in the file, not merely with its overall appearance. Verify that links go somewhere useful, controls operate, labels remain readable, and loading or empty states make sense. An attractive first screenshot can hide an unusable second state.

Use CSS inspection to investigate discrepancies. For responsive checks, Chrome’s device mode offers viewport simulation; confirm important mobile behavior on a real device as well. Record the tested conditions so a later reviewer knows what the result actually demonstrates.

7. Update decisions when the product changes

When an implementation reveals a better solution, update the brief alongside the code. Remove obsolete requirements rather than leaving contradictory instructions for the next pass. Keep a short change note for decisions whose reasoning would otherwise be lost.

The useful outcome is a repeatable collaboration: evidence becomes a brief, the brief guides an implementation, and the rendered implementation is checked against explicit criteria. The filename alone cannot provide that discipline; the quality of the decisions and the review does.
