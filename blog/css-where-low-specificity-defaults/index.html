Use :where() for CSS Defaults That Are Easy to Override

Write low-specificity component defaults with :where(). Compare selectors, keep cascade layers in mind and verify overrides without adding important flags.

By Penta AIPublished 14 November 20262 min read

In this guide

  1. Compare selectors that match the same element
  2. Do not confuse specificity with the entire cascade
  3. Keep defaults modest and behavior intact

Use :where() when a selector should match normally but contribute no specificity. It is useful for defaults that consumers should be able to override easily. The zero applies to the :where() expression and its arguments, not automatically to everything else in the selector.

Compare selectors that match the same element

:where(.article a) {
  color: #174fa0;
  text-underline-offset: .15em;
}
.article .quiet-link { color: #354052; }

The default selector contributes zero specificity, while the quiet-link rule has class specificity. Assuming equal origin, importance and cascade layer, the override can win without an ID selector or !important. This makes the default easier to reuse in a component library.

Reference: MDN :where() reference.

.article :where(a) { color: #174fa0; }
:where(.article a) { color: #174fa0; }

These two declarations illustrate a common trap. The first keeps the specificity of .article outside the function. The second puts the complete selector inside, so the whole selector contributes zero. Replacing :where() with :is() also changes specificity: :is() takes the highest specificity among its arguments.

Do not confuse specificity with the entire cascade

A low-specificity declaration can still win when a more important cascade stage favors it. Layers, origin and importance are considered before selector specificity. If an override fails, inspect the complete winning rule rather than concluding that :where() is broken.

For an existing stylesheet, convert one small default group first. Use a fixture containing a normal article link, a quiet variant and a link inside a nested component. Record which values should be inherited and which should be locally owned. This makes an accidental loss of styling visible before a broad reset change.

Keep defaults modest and behavior intact

  • Confirm the default still applies when no variant is present.
  • Check an override declared earlier as well as one declared later.
  • Inspect the computed winner and its cascade layer.
  • Retain visible focus and readable link distinctions.
  • Avoid adding !important just to compensate for an unclear selector contract.

Document the intended override point with the component. For broader rule conflicts, use the cascade debugging sequence. A low-specificity default is a maintenance choice, not a guarantee that every consumer rule should win.
