Use aria-busy While a Region Is Updating

Mark an incomplete interface update as busy, then clear the state on success or failure. Keep visible feedback and control behavior separate from announcements.

By Penta AIPublished 15 November 20262 min read

In this guide

  1. Define the region and the update boundary
  2. Separate readiness, announcements and interaction
  3. Review the paths that are easy to miss

Set aria-busy="true" while a region is undergoing an incomplete update, then return it to false when the update settles. This gives assistive technology information about the region’s readiness. It does not disable controls, show a spinner or perform the loading operation.

Define the region and the update boundary

<section id="results" aria-labelledby="results-title"
  aria-busy="false">
  <h2 id="results-title">Inspection results</h2>
  <div id="result-items"></div>
</section>
<p id="result-status" role="status"></p>
async function refreshResults(loadAndRender) {
  const region = document.querySelector("#results");
  const status = document.querySelector("#result-status");
  region.setAttribute("aria-busy", "true");
  status.textContent = "Updating results...";
  try {
    await loadAndRender();
    status.textContent = "Results updated.";
  } catch {
    status.textContent = "Could not update results. Please try again.";
  } finally {
    region.setAttribute("aria-busy", "false");
  }
}

The caller supplies the actual loading and rendering work. This example assumes updates are serialized, so only one refresh owns the busy state. Concurrent requests need explicit ownership or request tracking; an older request finishing must not clear the state of a newer update.

Reference: MDN aria-busy reference.

Separate readiness, announcements and interaction

The status region is outside the busy results region so its concise progress message is not part of the content being assembled. If the results themselves are a live region, busy can help defer announcements while multiple pieces change. Test the supported browser and screen-reader combinations; the attribute is not a promise about exact spoken timing.

Keep usable old results available when that matches the task, or explain why they are temporarily unavailable. If a control must not run twice, implement that behavior explicitly. Busy is not a substitute for disabled, inert or request deduplication.

Review the paths that are easy to miss

  • Complete a successful update and confirm busy returns to false.
  • Fail a request and verify an accurate retry message.
  • Cancel or replace a request and check state ownership.
  • Keep keyboard focus at a useful location while results change.
  • Check that visual progress and announcements describe the same operation.

Avoid marking the entire page busy for a small local update. Name the narrow region whose content is incomplete, and use the status-message workflow for concise results. The handoff should identify when the update starts, what “complete” means and who clears the busy state.
